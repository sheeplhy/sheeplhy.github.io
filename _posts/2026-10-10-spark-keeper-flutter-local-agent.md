> 火花管家（Spark Keeper）是我围绕 Flutter App、桌面执行端和个人数据安全做的一次学习实践。它希望帮助用户整理好友、消息与互动计划，但不会绕过验证码或平台安全验证，也不适合批量营销和陌生人触达。当前仓库是源码预览版，真实扫码、好友定位与发送流程仍需要账号本人在目标环境中完成验收。

**项目仓库：** [sheeplhy/spark-keeper](https://github.com/sheeplhy/spark-keeper)

## 1. 从一个容易忘记的小问题开始

维持日常互动并不复杂，但“记得给谁发、准备什么内容、在什么时间完成”会带来重复操作。最初的想法，是把好友、消息和时间计划集中到手机中管理，让手机承担轻量的配置工作。

真正需要谨慎处理的是登录状态。抖音 Cookie、浏览器会话和验证码都属于敏感信息，如果全部交给手机 App 或第三方业务服务器，使用方便了，安全边界却会变得模糊。

因此，火花管家没有把所有能力都塞进手机，而是拆成 **Flutter 控制端 + 用户自有执行端**：手机负责配置和查看状态，真正的网页操作仍留在自己的 Windows 电脑或自建服务器上。

## 2. 总体架构

```text
Flutter 手机 App
      │
      │  局域网 HTTP + 配对令牌
      ▼
Windows Agent ── Playwright ── 抖音网页版

或

Flutter 手机 App
      │
      │  HTTPS / 私有网络
      ▼
自建服务器 Agent ── Playwright ── 抖音网页版
```

这个拆分主要解决三个问题：

1. 手机不保存抖音 Cookie、密码和完整私信内容；
2. App 关闭后，定时计划仍可由执行端继续运行；
3. 网页结构变化时，可以单独维护 Agent，而不必把所有逻辑重新打进移动端。

移动端使用 Flutter 构建，当前依赖主要包括网络请求、二维码扫描、本地偏好存储和外部链接能力。执行端使用 Python 与 Playwright，通过用户本人登录的可见浏览器完成页面操作。

## 3. 为什么选择“控制端”和“执行端”分离

如果直接在手机里保存网页登录态，移动端需要承担更多敏感数据管理与浏览器自动化兼容问题。另一种常见做法是把任务全部交给公共服务器，但这意味着登录凭据可能离开用户控制的设备。

火花管家选择了相对保守的边界：

- 手机保存 Agent 地址、配对令牌和任务配置；
- Cookie 与 `storage-state.json` 只留在执行端；
- 手机只能获取二维码、连接状态和脱敏后的执行结果；
- 验证码、设备确认或 App 授权出现时，流程暂停并交还给用户。

这并不能消除所有风险，但能减少敏感登录信息在多个设备和接口之间流动。

## 4. 本地电脑与自建服务器两种模式

### 本地电脑模式

手机和电脑连接同一个可信 Wi-Fi，Windows Agent 提供局域网地址和随机配对令牌。除最小健康检查外，其余接口都需要令牌认证。

这种方式不依赖第三方业务服务器，适合在自己的电脑上运行和调试；限制也很直接：电脑必须保持开机、联网并持续运行 Agent，计划才能按时执行。

### 自建服务器模式

对于需要持续运行的场景，项目提供 Docker 部署配置。容器默认只监听服务器回环地址，外部访问需要用户自行配置 HTTPS 反向代理或私有网络。

我没有把“直接开放一个公网端口”作为默认方案，因为无 TLS 的接口和弱令牌会显著增加风险。服务器模式虽然更方便，但也要求使用者具备基本的部署和安全维护能力。

## 5. 任务与计划如何组织

手机端主要管理三类信息：好友、消息和执行计划。

- 好友通过准确昵称添加，可以单独暂停或删除；
- 消息支持随机选择或按顺序发送，也可以包含普通 Emoji；
- 计划同步到执行端后，由电脑或服务器负责调度。

这里有意没有把“好友数量不设产品上限”理解成鼓励批量发送。网页自动化存在平台风控与误操作风险，实际使用应该从一个好友和一条测试消息开始，并限制频率、确认对象，只操作自己的正常联系人。

## 6. Dry Run：先确认，再执行

我认为这个项目中最重要的交互不是“立即发送”，而是 **Dry Run（检查任务）**。

Dry Run 只检查登录状态、页面可用性和好友定位，不提交消息。用户确认昵称与目标正确后，再主动开始正式任务。存在重名、页面元素变化或结果无法确认时，程序应该停止并提示，而不是猜测目标或自动重试。

正式执行后，如果无法确定消息是否成功发送，也不会自动重复发送，以免同一好友收到多条相同内容。这种“宁可停下，也不盲目补偿”的策略，更适合带有外部副作用的自动化任务。

## 7. 安全与隐私边界

项目目前从几个方面限制敏感信息暴露：

- 配对令牌、Cookie、`.env`、`storage-state.json` 与运行日志不提交到 Git；
- 手机端和接口不返回 Cookie、密码、验证码或私信全文；
- 执行记录使用脱敏标识，并避免保存完整消息内容；
- 局域网 HTTP 只用于可信专用网络；
- 云端部署必须增加 HTTPS 或私有组网；
- 一旦出现验证码、设备确认或安全验证，自动流程立即暂停。

这些措施属于基础防护，不代表项目已经通过完整安全审计。特别是浏览器会话文件，一旦泄露就可能带来账号风险，因此仍需要用户妥善管理执行设备和备份。

## 8. 可选 AI 能力为什么不参与核心链路

项目预留了可选的部署助手，服务商、接口地址、Key 与模型由用户在 App 内自行配置。它可以帮助整理部署信息，但不会参与抖音登录、好友识别或消息发送。

这是一个刻意的产品边界：AI 可以提高说明、配置和排查效率，但账号认证、联系人选择和具有真实副作用的发送动作，仍应该由确定性的程序逻辑与人工确认控制。这样更容易解释结果，也能减少模型误判直接影响真实账号的风险。

## 9. 测试与当前完成度

截至源码预览版，项目已经完成：

- Flutter 静态分析与 7 项自动化测试；
- Flutter Web 构建；
- Python 文件编译检查；
- Agent 健康检查、401 鉴权、任务校验、计划保存与脱敏返回；
- Windows 安装、启动脚本和 Docker 部署配置。

与此同时，还有几项关键验收不能由无账号的自动化环境代替：

- Android 真机上的地址配置、二维码显示和扫码授权；
- 实际好友定位与重名确认；
- Dry Run 后的单次真实发送；
- App 关闭后的定时任务执行；
- 验证码和设备验证出现时是否能可靠暂停。

因此当前没有直接发布 Android APK。先公开源码与验收清单，再在真机完成关键流程后发布安装包，是比“先提供下载、再解释限制”更稳妥的顺序。

## 10. 局限与后续方向

火花管家依赖非官方网页自动化，抖音页面结构变化后，好友搜索、输入框和表情选择器都可能需要维护。自动操作也可能触发平台限制，因此项目无法承诺长期免维护运行。

后续更值得完善的方向包括：

- 补齐 Android 真机与 Windows 局域网联调；
- 为计划增加更明确的频率限制和失败原因展示；
- 加强重名联系人确认与任务预览；
- 完善 Agent 更新、备份和敏感文件清理流程；
- 在遵守平台规则的前提下，继续减少误操作和重复发送。

## 11. 这次实践带来的认识

这个项目让我进一步理解，App 开发不仅是完成页面和按钮，还要考虑数据存放位置、离线与后台行为、失败时的默认策略，以及用户是否能够理解并控制自动化过程。

火花管家目前仍是一个需要继续真机验证的个人项目，但“敏感凭据留在执行端、AI 不进入高风险核心链路、正式操作前先 Dry Run、无法确认时停止”这些设计原则，也可以迁移到其他带账号、设备和外部副作用的应用中。
